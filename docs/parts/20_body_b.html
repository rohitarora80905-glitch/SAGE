VI

Learning what a process will do: two engines

The Markov chain is the workhorse: fast, exact to count, and already near-perfect on patterned processes. The LSTM reads the whole history and is allowed to take over only where it proves better.

The Markov chain, counting a real processevents of one life of a fixed-pattern process from the replay, streamed into the transition table
Context tableswhat a first-order chain confuses

After releasing everything, does an escalating process start another level or exit? Does a cyclic process repeat or finish? The last event alone cannot tell. Two extra tables condition on the episode peak (most resources held since the process last held nothing) and the episode count (holding episodes completed in this life). Each context row is smoothed towards the plain row, and a context table is used only once it has beaten the plain table on both prequential log-likelihood and next-event hits.

Predictions are always masked to feasible events: no request of a held resource, no release of one not held. Drift is tracked with a CUSUM of the surprise of every event under the table in use.

The LSTM enginea recurrent network per process, trained online and gated

Input per event: the event, the holdings after it, the episode peak and the episode count. A -unit LSTM predicts the next event through a softmax masked to feasible events. Training is prequential: every event is scored before it is learned, then truncated back-propagation through time runs every events on the latest window and a replayed earlier one, four times as often during the first 256 events.

The gate. The network is used for a process only while it beats the Markov tables on a decayed prequential log-likelihood and on next-event hits, with at least 40 transitions seen. When it is in use, the table the rollout samples from is conditioned on the whole history: the row of the actual state is the network's forecast, every other row is the forecast after one hypothetical step. The rollout engine and the policy run unchanged.

The gate deciding, process by processdecayed prequential log-likelihood of the network against the tables over the replayed run; amber bands mark where the network was in use
Held-out accuracy of the two enginesnext-event top-1 over five unseen lives after three learned ones, three seeds, six slots each

Bursty processes are random by construction, so no model can predict them well; the network still learns from the holdings and episode structure how bursts end, and that is where the gate hands over. On patterned processes the chain is already near the ceiling and stays in charge.

VII

Trust, drift and the fallback

A rollout driven by a model that is wrong is worse than no rollout. SAGE checks its confidence first, and when it cannot trust the model it falls back to a safety check that needs no declaration either.

learned

Enough history, a predictable model, no drift: simulate K futures and gate on τ.

cold

Fewer than h_min = observed transitions: too little to simulate.

uncertain

Fitted average log-likelihood below min_ll = : the process is close to random, and a rollout from its model would be noise.

drift

CUSUM of surprise above drift_h = : a predictable process changed its behaviour. The flag clears after h_min fresh transitions once the CUSUM has fallen back.

The fallback: a safety check with learned claimsBanker's algorithm, with the declared maximum replaced by what the request log has shown

A process's claim is every resource it was ever seen to request plus what it holds; a process holding as many resources as it was ever seen holding at once is taken to release before asking for more. The check then runs the standard safety sequence: can every process finish, one after another, with what is free? With fallback = reactive the request is simply granted instead.

Recovery: partial rollbacka deadlock victim is rolled back only as far as needed

The victim is the cycle member aborted least often so far, preferring the process whose request closed the cycle. It releases everything and resumes from the last point of its program at which it held nothing, so finished work before that point is kept. Program steps undone are counted as wasted; the benchmark reports them per 1,000 events.

VIII

The six textbook rivals

Every policy runs on the same harness: the same programs, the same scheduler draws, the same exact deadlock detection on every block. Only the decision differs.

IX

Workloads: what the processes do

Synthetic processes with distinct personalities, generated from a seed so that every policy sees exactly the same traces. Each life of a process is a program of requests, releases and an exit; the slot respawns with a fresh program of the same type.

Families assign personalities to the six slots: fixed, bursty, escalating, mixed (two of each) and shift. The console's workload studio adds custom programs, hand-written or designed by the analyst from a description.

XII

The console

A FastAPI application served by uvicorn, with a front end that has no framework and no build step. Eight sections: overview, simulator, compare, workload studio, benchmark archive, verification, analyst and method.

How a run flows through the systemone request from the browser to a finished replay, and the analyst's side path to Groq
Jobs. A run, comparison, sweep or verification is a background job in a thread pool. The harness reports progress every 25 events through a callback that can also cancel the job; the browser follows it over server-sent events and fetches the result when it is done.
Payloads. The run record becomes JSON: summary metrics, binned time series, decision and deadlock logs, per-process model diagnostics and, with tracing on, one snapshot per event for the replay, including the outcome of every simulated future.
Analyst. The language model never takes part in a decision. It receives the evidence of a run as JSON and writes the report, explains one decision from the state at that event, designs workloads that the server validates, and answers questions with runs in context.

Limits and what comes nexthonest boundaries of the study
  • Single-instance resources only. The rollout's deadlock check is exact for that case; multi-instance resources would need the detection reduction throughout.
  • Synthetic workloads. The personalities are designed, not traced from real systems; the behaviour shift is a single engineered change.
  • The LSTM engine helps measurably only on the random processes. On patterned ones the chain is already at the ceiling, and the gate keeps it there.
  • Decision latency of a few milliseconds is fine for a simulator and for coarse-grained resources; it is far from a kernel lock path.
  • Next: real request traces, multi-instance resources, learned thresholds per process, and a kernel-side prototype of the learned-claims fallback alone.
