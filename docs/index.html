SAGE

Deadlock avoidance that learns what each process will do next.

The Simulated Ahead-of-Time Grant Evaluator removes the one thing Banker's algorithm cannot do without: declared maximum demands. Each process gets a behaviour model fitted from its own request log, every request for a free resource is tried in K simulated futures, and only the risky ones wait. This document covers the problem, the decision workflow, the two behaviour engines, a live replay of a real run, the full benchmark against six textbook strategies, the verification suite, the web console and the AI analyst.

I

The problem: deadlock, and the catch in every textbook answer

Two processes, two resources, two lock orders. Each holds one thing and waits for the other, and neither will ever move. An operating system can prevent this, avoid it, or detect it after the fact. Each option costs something.

A deadlock needs four conditions at once: resources that cannot be shared, processes that hold some while waiting for more, no pre-emption, and a circular chain of waiting. Break any one and deadlock is impossible. The textbook strategies differ only in which condition they attack, and when.

1Mutual exclusionA resource serves one process at a time.
2Hold and waitA process keeps what it has while asking for more.
3No pre-emptionNothing is taken away by force.
4Circular waitA cycle in the wait-for graph.
StrategyMechanismWhat it costs
PreventionRule out a condition by design (global lock order, timestamps as in wait-die and wound-wait)Rollbacks of innocent processes, rigid rules
AvoidanceKeep the system in a safe state by refusing requests that could lead to a cycle (Banker's algorithm)Every process must declare its maximum demand in advance
DetectionGrant everything, find cycles in the wait-for graph, abort a victimWasted work and rollbacks every time it happens

Avoidance is the attractive one: no rollbacks, no rigid ordering. Its catch is the declaration. Real programs rarely know, let alone announce, the most they will ever hold. SAGE keeps the avoidance idea and replaces the declaration with something the operating system already has: the history of what each process has asked for.

II

The idea: learn, simulate, then decide

Instead of asking a process what it might need, watch what it does, and before granting a request, play its near future forward many times.

1 · Learn from the request logper process, online, nothing declared

Every request, release and exit a process emits is counted into a behaviour model of that process alone: a Markov chain over its events with two context tables, and optionally a small LSTM that reads its whole history. Predictions are masked to what the process can actually do with what it holds.

2 · Simulate K futures of H stepsa sandboxed rollout from the live state

The allocation state is copied K times with the request granted. In each copy the processes are scheduled uniformly and act by sampling their models for H steps, with exact deadlock detection after every step. The futures run in lock-step as NumPy arrays, so a decision costs a few milliseconds.

3 · Gate on the share that deadlocksrisk ≥ τ means wait

The risk of a grant is the fraction of futures in which the requester ends up on a wait-for cycle. At or above the threshold τ the request is queued and re-evaluated at every release. When the model cannot be trusted, a Banker's-style safety check with learned claims decides instead.

The decision rule, in one line

For a request by process i for a free resource r, with a trusted model:

risk(i, r) = deadlocked futures / K        queue  if  risk ≥ τ
                                             grant  otherwise

With the project defaults, K = futures, H = steps and τ = . The simulation stops early as soon as the comparison with τ is settled: once enough futures have deadlocked to reach τ, or once even every unsettled future deadlocking could not reach it.

III

The live workflow of one request

Every request for a free resource travels the same pipeline. Pick a scenario and follow the token; the stages light up as the policy reaches them.

·Choose a scenario above or let it play.
Re-evaluationat every release, in arrival order

A queued request is not forgotten. Each release wakes the queue; every waiter whose resource is free is decided again on the current state. Requests the policy has already queued stay queued inside the sandbox too, so one queued request never counts as a threat to another.

Starvation guarddrain, then let the overdue request through

A request that has waited ticks in one go, or a process that has gone ticks without completing a life, is overdue. While one exists, processes that hold nothing are held back. They create no hold-and-wait, and the holders run on and release until the overdue request becomes safe.

Stall handler and recoverywhen nothing is runnable

If every process is waiting and some are queued by policy, the queued request with the lowest re-scored risk is force-granted. A deadlock that still occurs is detected exactly and resolved by aborting the cycle member aborted least often, rolled back only to the last point at which it held nothing.

Simulating…

The rollout engine keeps all K futures in one set of arrays of shape (K, n, m) and advances them together: blocked processes acquire their resource as soon as it is free, one runnable process per future is drawn uniformly and samples its next event from its model, restricted to what it can do with what it holds, and after every step the futures in which the requester waits are checked for a cycle. A future is settled when it deadlocks or when the requester finishes its life.

Because the policy only compares the risk with τ, the simulation stops as soon as that comparison can no longer change. That is why queued decisions often show fewer than K futures examined: the verdict was already certain.

VI

Learning what a process will do: two engines

The Markov chain is the workhorse: fast, exact to count, and already near-perfect on patterned processes. The LSTM reads the whole history and is allowed to take over only where it proves better.

The Markov chain, counting a real processevents of one life of a fixed-pattern process from the replay, streamed into the transition table
Context tableswhat a first-order chain confuses

After releasing everything, does an escalating process start another level or exit? Does a cyclic process repeat or finish? The last event alone cannot tell. Two extra tables condition on the episode peak (most resources held since the process last held nothing) and the episode count (holding episodes completed in this life). Each context row is smoothed towards the plain row, and a context table is used only once it has beaten the plain table on both prequential log-likelihood and next-event hits.

Predictions are always masked to feasible events: no request of a held resource, no release of one not held. Drift is tracked with a CUSUM of the surprise of every event under the table in use.

The LSTM enginea recurrent network per process, trained online and gated

Input per event: the event, the holdings after it, the episode peak and the episode count. A -unit LSTM predicts the next event through a softmax masked to feasible events. Training is prequential: every event is scored before it is learned, then truncated back-propagation through time runs every events on the latest window and a replayed earlier one, four times as often during the first 256 events.

The gate. The network is used for a process only while it beats the Markov tables on a decayed prequential log-likelihood and on next-event hits, with at least 40 transitions seen. When it is in use, the table the rollout samples from is conditioned on the whole history: the row of the actual state is the network's forecast, every other row is the forecast after one hypothetical step. The rollout engine and the policy run unchanged.

Bursty processes are random by construction, so no model can predict them well; the network still learns from the holdings and episode structure how bursts end, and that is where the gate hands over. On patterned processes the chain is already near the ceiling and stays in charge.

VII

Trust, drift and the fallback

A rollout driven by a model that is wrong is worse than no rollout. SAGE checks its confidence first, and when it cannot trust the model it falls back to a safety check that needs no declaration either.

learned

Enough history, a predictable model, no drift: simulate K futures and gate on τ.

cold

Fewer than h_min = observed transitions: too little to simulate.

uncertain

Fitted average log-likelihood below min_ll = : the process is close to random, and a rollout from its model would be noise.

drift

CUSUM of surprise above drift_h = : a predictable process changed its behaviour. The flag clears after h_min fresh transitions once the CUSUM has fallen back.

The fallback: a safety check with learned claimsBanker's algorithm, with the declared maximum replaced by what the request log has shown

A process's claim is every resource it was ever seen to request plus what it holds; a process holding as many resources as it was ever seen holding at once is taken to release before asking for more. The check then runs the standard safety sequence: can every process finish, one after another, with what is free? With fallback = reactive the request is simply granted instead.

Recovery: partial rollbacka deadlock victim is rolled back only as far as needed

The victim is the cycle member aborted least often so far, preferring the process whose request closed the cycle. It releases everything and resumes from the last point of its program at which it held nothing, so finished work before that point is kept. Program steps undone are counted as wasted; the benchmark reports them per 1,000 events.

VIII

The six textbook rivals

Every policy runs on the same harness: the same programs, the same scheduler draws, the same exact deadlock detection on every block. Only the decision differs.

IX

Workloads: what the processes do

Synthetic processes with distinct personalities, generated from a seed so that every policy sees exactly the same traces. Each life of a process is a program of requests, releases and an exit; the slot respawns with a fresh program of the same type.

Families assign personalities to the six slots: fixed, bursty, escalating, mixed (two of each) and shift. The console's workload studio adds custom programs, hand-written or designed by the analyst from a description.

XII

The console

A FastAPI application served by uvicorn, with a front end that has no framework and no build step. Eight sections: overview, simulator, compare, workload studio, benchmark archive, verification, analyst and method.

How a run flows through the systemone request from the browser to a finished replay, and the analyst's side path to Groq
Jobs. A run, comparison, sweep or verification is a background job in a thread pool. The harness reports progress every 25 events through a callback that can also cancel the job; the browser follows it over server-sent events and fetches the result when it is done.
Payloads. The run record becomes JSON: summary metrics, binned time series, decision and deadlock logs, per-process model diagnostics and, with tracing on, one snapshot per event for the replay, including the outcome of every simulated future.
Analyst. The language model never takes part in a decision. It receives the evidence of a run as JSON and writes the report, explains one decision from the state at that event, designs workloads that the server validates, and answers questions with runs in context.

XIV

Reproduce everything

Python 3.10 or newer, NumPy and Matplotlib for the simulator; PyTorch for the LSTM engine; FastAPI, uvicorn and the Groq SDK for the console. No GPU.

Commandsfrom the sage_project folder 
pip install -r requirements.txt
python tests/verify.py              # the verification suite
python -m experiments.run_all       # headline benchmark, about 20 minutes
python -m experiments.compare_all   # every policy, 100 seeds
python -m server                    # the console at http://127.0.0.1:8000
python ../docs/build_data.py        # regenerate this document's data
python ../docs/build.py             # rebuild this document

The analyst needs a Groq API key: set GROQ_API_KEY, put it in sage_project/.env, or paste it in the console's Connect AI dialog, which also lists the models available to the key.

Limits and what comes nexthonest boundaries of the study
  • Single-instance resources only. The rollout's deadlock check is exact for that case; multi-instance resources would need the detection reduction throughout.
  • Synthetic workloads. The personalities are designed, not traced from real systems; the behaviour shift is a single engineered change.
  • The LSTM engine helps measurably only on the random processes. On patterned ones the chain is already at the ceiling, and the gate keeps it there.
  • Decision latency of a few milliseconds is fine for a simulator and for coarse-grained resources; it is far from a kernel lock path.
  • Next: real request traces, multi-instance resources, learned thresholds per process, and a kernel-side prototype of the learned-claims fallback alone.
