SAGE: deadlock avoidance that learns what processes will do next

Simulated Ahead-of-Time Grant Evaluator · Harvi Bhavin Patel (24BCE2557) · Srishti Saluja (24BCE2587) · Supervisor: Perepi Rajarajeswari

Before granting a resource, SAGE simulates short futures of the system from each process's learned behaviour and queues the request if too many of those futures end in a deadlock. It needs no declared maximum demand, which the classic Banker's Algorithm requires and real systems rarely have.

Background

The deadlock problem

A deadlock is a set of processes in which each one waits for a resource that another one in the set holds. None of them can move, so none of them will ever release what it holds. With single-instance resources, a deadlock is exactly a cycle in the wait-for graph: an arrow from each waiting process to the process holding what it waits for.

Four conditions must hold at once (Coffman et al.): mutual exclusion (a resource has one holder), hold and wait (a process keeps what it has while asking for more), no preemption (resources are not taken away) and circular wait. Every deadlock-handling method breaks one of these, or detects the result and undoes it.

Methods compared

Ways to handle deadlocks

Operating systems texts group the methods into prevention (make a deadlock structurally impossible), avoidance (only grant requests that keep the system safe) and detection with recovery (let it happen, notice it, undo it). SAGE is an avoidance method that learns instead of being told. All eight methods below run in the same simulator on the same workloads and seeds.

How it works

How SAGE decides

Every request for a free resource reaches SAGE (a request for a held resource simply blocks, as in every method). SAGE first asks whether it can trust its model of the requesting process, then takes one of two routes.

Trace a request from

The simulation route: K futures, H steps

For a process it can predict, SAGE copies the live state K = 100 times, applies the hypothetical grant in each copy, and plays every copy forward for H = 30 events. In each future the scheduler picks one runnable process at random, as the real scheduler does, and that process does what its behaviour model says is likely next, limited to what it can actually do with what it holds. Requests that SAGE has already queued stay queued. A future counts as deadlocked if the requester ends up on a wait-for cycle. The risk is the share of deadlocked futures; the request is queued if the risk is at least τ = 0.10. The simulation stops as soon as the answer is certain.

Request

The safety-check route: learned claims

For a process SAGE cannot predict (a near-random process, too little history, or behaviour that has just changed), simulation would be noise. SAGE instead runs a Banker's-style safety check, using learned claims in place of declared maxima: the set of resources the process has ever been seen to request, from its own request log. A process already holding as many resources as it has ever held at once is taken to release before it asks for more. Nothing has to be declared in advance.

Keeping every process moving

  • Starvation guard. If a process has waited 400 events in one go, or gone 900 events without finishing a life, processes that hold nothing are held back until it gets through. Holding back an idle process creates no hold-and-wait, so this never causes a deadlock.
  • Stall handler. If every process is waiting, the queued request with the lowest freshly computed risk is released (overdue requests first).
  • Recovery. If a deadlock does form, the member rolled back least often is chosen as the victim and rolled back only to the last point where it held nothing, so finished work is kept.

Learning

Learning what each process will do

Each process slot has its own behaviour model, trained online from its request log: every request, release and exit it emits.

Markov chain
The core model: the probability of each next event given the last one, restricted to events the process can perform with what it holds (it cannot release what it does not hold).
Two context tables
Indexed by the episode peak (most resources held since it last held nothing) and the episode count (episodes finished this life). They tell "another level / cycle" from "exit". A process switches to one only after it has out-predicted the plain chain.
Confidence checks
Cold: fewer than 20 observed events. Uncertain: the fitted model is close to random. Drift: a CUSUM of surprise crosses its threshold, meaning the behaviour has changed. Any of these sends the request to the safety-check route.

How well the model predicts unseen process lives

History before testing

The model learns the first lives of a process type and then predicts fresh lives without learning from them; both versions see exactly the same lives (20 seeds). A fixed-pattern process repeats its cycle a random 4 to 8 times, so with only three lives of history no model can foresee its exit: the two versions predict identically there.

History

From v1 to v2

The first version ran and passed its tests, but its results were weak: on random workloads it caused more deadlocks than simply granting everything, and it queued about a third of all requests. Tracing every deadlock back to the grant that created it showed where they came from.

Deadlocks over seeds 0 to 4, split by how the resources on the deadlock cycle were granted. In v1 almost none came from SAGE's own risk decisions: they came from the blind fallback (which granted unpredictable processes' requests unchecked) and from the stall handler (which used stale scores).

Prediction quality

Early warning and behaviour drift

In shadow mode SAGE watches a system that grants everything and only reports the requests it would have queued. Both versions watch the same trace, so they face the same deadlocks. A deadlock is warnable if a process in its cycle made any request since the previous deadlock; otherwise no per-request predictor can see it coming.

When behaviour changes

In the behaviour-shift workload, half of the processes change their acquisition order at event 600, creating a conflict that did not exist before. v2 checks a CUSUM of each event's surprise after every event, so it flags a predictable process after two or three events it has never shown before.

Cost

Decision cost

The classic methods decide in microseconds; SAGE takes milliseconds because it simulates. v2 stops simulating once the answer is certain, skips futures whose outcome is settled, and decides unpredictable processes with a safety check instead of a simulation. Both versions were timed in the same session, alternately, best of two, each cell averaged over five seeds.

Scope

Limits and how to reproduce

  • Banker's Algorithm with true maximum demands never deadlocks; SAGE keeps deadlocks low without that information but does not reach zero.
  • On near-random workloads SAGE v2’s deadlock rate grows with the size of the system (about 1 per 1,000 events at 4 processes, about 10 at 10 processes; Section 08).
  • Learned claims cover only resources a process has used before; a process that starts using a new resource is covered after its first use.
  • The workloads are synthetic and resources are single-instance; results on real traces have not been measured.
  • SAGE's settings were chosen on these workload families; the separate seed sets guard against fitting to particular seeds, not to the families themselves.
  • A SAGE decision costs milliseconds: suitable for admission-style decisions, too slow for per-instruction locking.
